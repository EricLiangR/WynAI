## 1. 目标和原则

本计划用于验证周黑鸭 AI POC 总体方案中的关键技术假设，形成可复核的证据，再决定正式开发和客户联合验收的范围。

验证遵循以下原则：

- 先验证外部依赖和高风险边界，再扩大功能开发范围。
- 代码静态检查、自动化测试、真实 Wyn 联调和客户 UAT 分开记录，不能相互替代。
- Wyn 负责权限、数据查询、仪表板运行和原生监控；WynAI 负责语义编排、证据验证、归因和智能解读。
- 不使用业务字段硬编码、截断后继续计算、抽样冒充全量、本地重建 Wyn 结果或业务 fallback。
- 所有通过结论必须有输入、执行、输出和日志证据；没有 Wyn 环境或 API 文档时标记为“待外部验证”。
- 第一轮采用最小可行验证，不要求立即实现完整插件、完整监控中心或 100,000 行压力能力。

### 2.1 第一轮的退出目标

第一轮验证完成后，必须能够回答以下问题：

1. E_04 是否可以采用官方插件/宿主 API；如果不行，网络捕获兼容层的边界是什么。
2. E_03 是否可以复用当前 `InsightInput`、Evidence Pack、Critic/Narrator 和贡献分析基础。
3. E_05 的限制应配置在哪一层，以及是否需要保持 20,000 行而不是贸然提升。
4. E_01 是否具备开始专项准确率评测的最小数据条件。
5. 最后确认 E_02 是否可以采用 Wyn 原生监控作为检测和通知底座，并补齐主动告警到 AI 诊断的端到端闭环。

## 4. 验证工作流

每一个验证项都按以下步骤执行：

1. 记录假设、输入版本、账号和环境。
2. 设计最小测试用例，先覆盖成功、失败和边界路径。
3. 执行代码检查、自动化测试或真实环境操作。
4. 保存原始响应、日志、截图、结果和错误信息。
5. 判断为“通过、部分通过、失败、待外部验证”之一。
6. 把结论、限制和后续任务回填本文档，不把推测写成根因。

### 4.1 证据等级

| 等级 | 证据 | 可支持的结论 |
| --- | --- | --- |
| L0 | 方案讨论或代码阅读 | 只能说明设计假设 |
| L1 | 静态检查、单元测试、固定输入测试 | 证明局部代码行为 |
| L2 | 本地端到端或隔离服务测试 | 证明项目链路集成行为 |
| L3 | 真实 Wyn API/真实看板/真实账号联调 | 证明平台集成可行 |
| L4 | 周黑鸭真实数据、真实浏览器和客户验收 | 证明 POC 用例通过 |

## 5. P0-A：E_02 Wyn 数据监控验证

### 5.1 验证目标

确认 Wyn 原生数据监控可以承担 E_02 的调度、异常检测、灵敏度和消息推送，并能为 WynAI 提供足够的异常上下文。

### 5.2 最小验证用例

| 编号 | 用例 | 预期 |
| --- | --- | --- |
| E02-API-01 | 创建销售额监控 | 返回稳定的监控 ID、规则版本和执行计划 |
| E02-API-02 | 更新阈值和灵敏度 | 更新后规则生效，有审计记录 |
| E02-API-03 | 注入门店销售额下降 30% | 告警定位到指标、门店、期间和变化幅度 |
| E02-API-04 | 注入品类动销率骤升 | 告警定位到品类级 |
| E02-API-05 | 调低/调高灵敏度 | 触发行为随配置变化，正常波动可抑制 |
| E02-API-06 | 查询执行历史 | 可以查询成功、未触发和失败记录 |
| E02-API-07 | webhook 或事件历史 | 能拿到唯一 event ID 和 Wyn 执行引用 |
| E02-API-08 | 企微/邮件推送 | 消息送达，失败可重试或查询原因 |
| E02-API-09 | 停用和恢复规则 | 停用后不触发，恢复后按新版本执行 |
| E02-API-10 | 受限账号执行 | 监控不突破账号数据权限 |

### 5.3 通过标准

- 创建、修改、停用和查询接口可用，或有明确的人工配置替代流程。
- 至少两类异常均可识别并定位到门店/品类级。
- 灵敏度配置确实影响触发行为。
- 至少一个通知渠道真实送达。
- 存在 webhook 时验证签名、重试和幂等；不存在时记录“诊断链接方案”。
- 异常事件可映射为 `AnomalyEvent v1`，不需要 WynAI 猜测缺失的指标或对象。

### 5.4 输出物

- `E02-Wyn监控API能力矩阵.md`
- 创建/修改/触发/通知的脱敏请求和响应样例
- 异常事件样例和通知截图
- Wyn 版本、权限和接口限制记录

## 6. P0-B：E_04 看板插件和数据获取验证

### 6.1 验证目标

确认一个 Wyn 看板在当前版本和用户权限下，能否采集形成完整、同一筛选状态的 `DashboardSnapshot`，并转换为现有 `InsightInput v1`。

### 6.2 验证顺序

1. 官方插件/宿主 API。
2. Wyn 官方查询或导出 API。
3. 仅针对确认过的接口使用服务端白名单网络捕获。

不得把“可以监听到某个请求”直接等同于“已经获取完整看板数据”。

### 6.3 最小验证范围

- 一张 A 系列门店经营看板。
- 2–4 个核心组件：总销售额、销售趋势、门店排名、品类分布。
- 一个全局筛选和一个组件筛选。
- 一个已加载状态、一个加载失败状态、一个无权限或无数据状态。

### 6.4 验证项

| 编号 | 验证项 | 通过条件 |
| --- | --- | --- |
| E04-DATA-01 | 识别看板 ID、版本和标题 | 信息稳定且可记录 |
| E04-DATA-02 | 获取全局/组件筛选 | 快照中保留实际生效状态 |
| E04-DATA-03 | 获取组件结果 | 每个组件有独立结果集 ID |
| E04-DATA-04 | 获取业务元数据 | 有数据集、指标、维度、单位或查询引用 |
| E04-DATA-05 | 快照一致性 | 组件共享同一过滤状态和捕获批次 |
| E04-DATA-06 | 状态完整性 | 加载中、失败、无权限、空结果不被静默丢弃 |
| E04-DATA-07 | InsightInput 转换 | 通过现有协议校验，保留质量和来源信息 |
| E04-DATA-08 | 过滤后刷新 | 改变筛选后不会混入旧结果 |
| E04-DATA-09 | 权限边界 | 受限账号只能看到有权限的组件数据 |
| E04-DATA-10 | 版本兼容 | 目标 Wyn 版本可重复获取 |

### 6.5 通过标准

- 至少 2 个核心组件可以形成同一快照。
- 快照可以转换为 `InsightInput v1` 并被数据洞察模块接收。
- 过滤状态、组件状态、数据集和查询来源不会丢失。
- 抽查 5 个数值时，组件展示值与输入结果一致。
- 如果只能通过网络捕获，必须明确列出接口白名单、版本范围和失效检测方式。

### 6.6 输出物

- `DashboardSnapshot v1` 脱敏样例
- 插件/宿主 API 能力矩阵
- 组件状态和快照一致性测试记录
- 网络捕获兼容方案及风险说明（如使用）

## 7. P1-A：E_03 证据化归因验证

### 7.1 验证目标

在不依赖完整 E_02/E_04 集成的情况下，用固定的异常事件和 Wyn 查询结果验证当前数据洞察链路是否能支撑 E_03。

### 7.2 输入准备

- 一个门店销售额下降 30% 的异常事件。
- 当前期和基准期总销售额结果。
- 品类、时段、客流三个维度的分组结果。
- 一个没有明显贡献项的负向样例。
- 每个结果集的查询引用、数据集、筛选、期间和质量状态。

### 7.3 验证项

| 编号 | 验证项 | 通过条件 |
| --- | --- | --- |
| E03-INS-01 | 异常复现 | 总变化和异常事件一致 |
| E03-INS-02 | 品类拆解 | 每个贡献值可由结果计算得到 |
| E03-INS-03 | 时段拆解 | 支持时段粒度或明确返回不可用 |
| E03-INS-04 | 客流拆解 | 支持客流维度或明确返回不可用 |
| E03-INS-05 | 总量对账 | 分组变化和总变化在同一口径下相等 |
| E03-INS-06 | 主因排序 | 按异常方向排序，保留反向抵消项 |
| E03-INS-07 | 数值证据 | 所有数字绑定 evidence ID 且可验证 |
| E03-INS-08 | 无主因 | 输出“未找到显著主因”，不硬凑结论 |
| E03-INS-09 | 截断/样本 | 受限结果不生成全局主因结论 |
| E03-INS-10 | 因果措辞 | 输出使用“贡献/拖累/关联”，不宣称统计因果 |

### 7.4 通过标准

- 异常方向和主因排序与固定答案一致。
- 抽查数值误差为 0。
- 维度结果能够和总结果对账；不能对账时停止主因结论。
- 无主因样例进入明确的 inconclusive 路径。

## 8. P1-B：E_05 超限熔断验证

### 8.1 验证目标

确认当前 20,000 行硬限制的行为、配置入口、边界和故障恢复，并决定是否需要评估更高阈值。

### 8.2 验证项

| 编号 | 验证项 | 通过条件 |
| --- | --- | --- |
| E05-LIM-01 | 当前硬限制 | 超限返回 `QUERY_RESULT_EXCEEDS_LIMIT` |
| E05-LIM-02 | 不截断计算 | 不使用前 N 行生成业务答案 |
| E05-LIM-03 | 阈值配置 | 配置可读取、受权限控制并有审计 |
| E05-LIM-04 | 阈值 - 1 | 正常返回 |
| E05-LIM-05 | 阈值 | 按约定边界正常返回或明确阻断 |
| E05-LIM-06 | 阈值 + 1 | 阻断并提示缩小范围 |
| E05-LIM-07 | 多次超限 | 连续超限后服务仍可用 |
| E05-LIM-08 | 并行正常请求 | 其他问数和看板不受影响 |
| E05-LIM-09 | 用户主动限量 | 与平台硬上限区分，不绕过安全上限 |
| E05-LIM-10 | 100,000 评估 | 若要提升，提供内存、延迟和超时证据 |

### 8.3 通过标准

- 超限 100% 被拦截，有可读提示和缩小范围建议。
- 无截断后继续计算或业务 fallback。
- 阈值语义明确：匹配行、返回行、分组数和 AI 结果集分开配置。
- 服务恢复和并行请求通过。

## 12.2 首轮本地验证结论

### 已验证

- 当前 InsightInput v1 能拒绝 Schema/字段/类型错误，并保留指标语义和派生公式。
- 当前数据洞察链路能从固定输入生成证据目录，Critic/Narrator 数值声明校验相关测试通过。
- 当前受控查询在超过 20,000 行时返回 `QUERY_RESULT_EXCEEDS_LIMIT`，不会截取前 20,000 行继续生成答案。
- 当前结果完整性校验覆盖零行结果、服务端计数与返回行数不一致、聚合后筛选超限等场景。
- 当前项目相关 JavaScript 语法检查通过。

### 尚未验证

- 没有周黑鸭 DS-7/DS-8/A 系列真实数据的专项结果，因此不能宣称 E_01–E_04 客户用例通过。
- 当前仓库没有可直接复用的 Wyn 数据监控 CRUD；但真实 UI 请求已确认 `POST /api/data/monitorings` 存在，Email 通知和每次触发策略已在请求中出现。接口是否稳定、是否支持 WeCom、事件回调和权限模型仍需目标实例验证。
- 本地 V1 Swagger 已确认 DataMonitoring 端点集合：创建、批量删除、列表、更新、info、detail、count、批量启停、重命名和描述更新；只读列表和只读总数已在当前本地会话实际返回成功。当前实例返回 1 条监控，列表摘要显示其状态为 `Failed`、`alarmStatus=true`，并提供最近执行/告警/错误时间。Swagger 文档没有给出明确响应模型、鉴权说明或通知渠道枚举。
- Wyn v9.1 官方文档已确认 `GET /api/v2/dashboard/dashboards/{id}`、`GET /api/v2/dashboard/dashboards/{dashboardID}/pivotData` 和 Dashboard 导出接口，并确认自定义可视化可通过 `wyn-visual-tools` 初始化、开发、打包为 `.viz`、上传 Resource Portal 后加入看板；但尚未证明插件能稳定获取所有兄弟组件的完整同快照数据。
- 本机 `wyn-visual-tools 6.1.8` 已完成最小插件初始化、依赖安装、开发编译、开发服务器启动和生产 `.viz` 打包。生成的 `visual.d.ts` 证明插件可接收自身 `dataViews`、`filters`、`watchedParameters` 和宿主服务，但没有发现读取其他可视化组件网络响应的标准接口；因此网络监听仍只能作为版本绑定的兼容层假设。
- Swagger 的监控 `info` 和 `detail` 操作都把 `{id}` 同时保留在路径和 query 参数中，当前 UI 调用均返回 `errorCode=10002`（`Entity not found`）。这属于需要先修正或绕过的 API 合同问题，不能直接据此判断详情后端不可用；修正路径的直接浏览器导航又被当前浏览器拦截，后续应在同源开发工具或受控 API 客户端中做一次不落盘的 GET 验证。
- 当前测试证明的是固定上限 20,000 行的阻断行为，不证明阈值已经配置化，也不证明 100,000 行可安全运行。

### 当前决策

基于首轮结果，E_03 和 E_05 可以进入小范围实现/补强；E_02 已从“无接口证据”推进到“存在内部创建接口，待实例联调”，E_04 已从“方案假设”推进到“官方 API 和插件开发路径已确认，待目标看板联调”；E_01 先完成 DS-7 数据和题库冻结。

## 12.3 Wyn API 查阅结果

### E_02：已观察到的监控创建接口

用户提供的真实浏览器请求已脱敏分析。请求使用当前 Wyn 实例的同源内部接口：

```text
POST /api/data/monitorings
Content-Type: application/json
```

该请求体至少包含以下结构：

| 字段 | 作用 | 已观察内容 |
| --- | --- | --- |
| `dashboardId` | 绑定看板 | 有 |
| `name` | 监控名称 | 有 |
| `query.documentId` | 查询所属文档 | 有 |
| `query.aggregateModels` | 聚合模型 JSON 字符串 | 有，包含维度和 `cnt` 聚合 |
| `query.filters` | 过滤条件 JSON 字符串 | 有 |
| `query.values` | 当前值 JSON 字符串 | 有 |
| `query.dimensions` | 维度 JSON 字符串 | 有 |
| `query.field` | 监控字段/指标显示名 | 有 |
| `condition.operator` | 条件操作符 | 已观察 `>=` |
| `condition.threshold` | 阈值 | 有 |
| `notifications` | 通知渠道和联系人 | 已观察 `Email`、联系人和模板 |
| `notificationStrategy` | 通知策略 | 已观察 `Notification_On_Every_Trigger`、60 分钟窗口 |
| `executionPlan` | 执行计划 | 已观察开始时间、时区、Cron pattern |

这证明 E_02 的“创建监控”方向可行，但当前证据仍属于**UI 内部 API 观察结果**，不是公开 Server API 合同。正式接入前必须验证：

- 是否有稳定的 GET/PUT/DELETE 监控接口以及监控 ID 返回值。
- 请求中的 `aggregateModels`、`filters`、`values`、`dimensions` 是否必须保持 JSON 字符串格式。
- `condition` 是否支持同比/环比、相对变化百分比、连续触发次数和最低业务量。
- `notifications.channel` 是否支持 WeCom；目前公开 Wyn Alerts 页面明确提到 Slack、MS Teams 和 Email，但没有证明 WeCom。
- 是否存在 webhook、事件历史查询或可供 AI 诊断关联的执行 ID。
- Anti-forgery、会话 Cookie、服务账号和权限校验如何处理。不能把浏览器 Cookie 固化到 WynAI 配置中。
- 接口是否属于当前版本私有实现，升级后是否有兼容保证。

本地 V1 Swagger 暴露的端点如下：

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| POST | `/api/data/monitorings` | 创建监控 |
| DELETE | `/api/data/monitorings` | 按 `idList` 批量删除 |
| GET | `/api/data/monitorings?orderby=&limit=&offset=` | 分页列表 |
| PUT | `/api/data/monitorings/{id}` | 更新监控 |
| GET | `/api/data/monitorings/info/{id}` | 获取监控信息 |
| GET | `/api/data/monitorings/detail/{id}` | 获取监控详情 |
| GET | `/api/data/monitorings/count` | 获取监控数量 |
| PUT | `/api/data/monitorings/status` | 按 `idList` 批量启用/停用 |
| PUT | `/api/data/monitorings/rename/{id}` | 更新名称 |
| PUT | `/api/data/monitorings/description/{id}` | 更新描述 |

Swagger V1 的创建/更新模型还明确列出 `encryptReferenceToken`、`createdByIntegration`、用户/租户字段、通知策略 `totalSeconds` 和执行计划字段。当前 V2 Swagger 未检索到 DataMonitoring，后续接入必须绑定实际 Wyn 版本和 V1 内部 API，不应假设 V2 同样存在。

### E_04：官方文档已确认的能力

Wyn 官方 v9.1 文档确认以下 Server API：

| API | 作用 | 对 E_04 的价值 |
| --- | --- | --- |
| `GET /api/v2/dashboard/dashboards/{id}?rev={revision}` | 获取 DashboardViewModel | 获取看板 ID、版本、页面、场景、参数和共享资源 |
| `GET /api/v2/dashboard/dashboards/{dashboardID}/pivotData` | 获取场景 Pivot 数据，支持 `scenarioName`、`scenarioId`、`scenarioTitle`、`lng` | 可作为组件/场景数据快照候选入口 |
| `GET /api/v2/dashboard/dashboards/{id}/export` | 导出 PDF、PNG 或 PPT | 支持看板原生导出验证，但不等同于 AI 解读导出 |

官方自定义可视化文档还确认：

1. 使用 `@wynenterprise/wyn-visual-tools` 初始化项目。
2. 使用 `wyn-visual-tools develop` 启动开发服务。
3. 管理员需要开启 Dashboard Developer Mode。
4. 通过 `visual.json` 和 `capabilities.json` 配置元信息、数据绑定、检查器和操作栏。
5. 使用 `wyn-visual-tools package` 生成 `.viz` 文件并上传 Resource Portal。
6. 上传后可以在 Dashboard Designer 中使用该自定义可视化。

因此，E_04 的“可视化插件作为入口”已经有官方产品路径支持。仍需在目标 Wyn 实例中验证插件是否能读取其他组件的查询结果；官方 Dashboard API 返回模型/场景数据，并没有在公开文档中直接承诺插件可以监听或读取所有兄弟组件的网络响应。
